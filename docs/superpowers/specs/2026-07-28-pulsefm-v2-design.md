# PulseFM v2 — Design

Date: 2026-07-28
Status: Approved

## Context

PulseFM is a 24/7 AI-generated lofi radio station. Listeners vote on the vibe of the
next track; the winning option is generated by a music model and plays when the
current track ends.

v1 exists and runs (`~/Documents/repos/pulseFM`): a Next.js client on Vercel, five
Python Cloud Run services, three Cloud Functions, Firestore, Memorystore Redis,
Pub/Sub, Eventarc, and Cloud Tasks. It works, and its `docs/adr/` records the
reasoning behind four hardening decisions that this design deliberately inherits.

v2 is a rebuild in a new repository (`~/Documents/repos/pulsefm-v2`) with a different
delivery shape — React on Firebase Hosting, Google API Gateway as the auth and
routing layer — and a much smaller service surface. v1 is reference material, not a
migration source. Nothing is ported verbatim except where this document says so.

The frontend design is fixed by a high-fidelity handoff in
`design_handoff_pulse_fm_player/`.

## Goals

- A single synchronized station: every listener hears the same track at the same
  offset.
- Authenticated listeners vote on the vibe of the next track, one vote each.
- Unauthenticated listeners can listen and watch the poll, but not vote.
- The poll opens with the current track and closes early enough that the winning
  track can be generated before the current one ends.
- The radio service reflects a newly available song immediately, with no propagation
  delay between generation and availability.
- Two Python services on Cloud Run, consolidated behind Google API Gateway.

## Non-goals

- Seeking, scrubbing, prev/next, and volume. The design handoff explicitly excludes
  them.
- Multiple stations. `station/current` is a single document by design.
- A user-visible song history or library.
- Retrying failed generations. The fallback backlog covers the gap, matching v1
  ADR 0004's accepted behaviour.
- Migrating v1 data or users. v2 starts empty.

## Decisions

### D1 — Discrete tracks over a public CDN, not a continuous stream

The radio service publishes a snapshot; the client fetches an `.m4a` from a public
GCS bucket behind Cloud CDN and seeks to `serverNow - startAt`.

Rejected: playlist-driven HLS. HLS players buffer 6–30s behind the live edge and
different listeners buffer differently, so a listener would vote on the next track's
vibe while still hearing the previous one. That desync undermines the core mechanic.
HLS also cannot supply the per-track progress bar and timecodes the design requires,
so the snapshot API would be built regardless.

Rejected: v1's private bucket with session-gated signed URLs (ADR 0006). Its privacy
rationale does not survive the requirement that unauthenticated listeners can listen —
the audio is anonymously reachable either way — and signed URLs defeat shared HTTP
caches, so egress would scale with listener count.

### D2 — Firestore only; no Redis

Vote dedupe is a document create at `polls/{pollId}/votes/{uid}`. A create fails if
the document exists, so dedupe is atomic with no transaction, no read-modify-write,
and no single-document write contention.

Firestore is strongly consistent, so a worker's `status: ready` write is visible to
the radio service's very next read. This is the "reflect immediately" requirement,
satisfied by the store's own guarantee rather than by an invalidation mechanism.

Rejected: Memorystore Redis (v1's shape). ~$40–60/month fixed plus a VPC connector,
and it forces both services onto a VPC. Rejected: Upstash. A non-GCP dependency in
the vote hot path for a benefit that D6 removes anyway.

### D3 — Two services, split by traffic profile

- `station-api` — public, reached only through API Gateway. Read-heavy, autoscales
  with listeners. Serves state and queue, accepts votes.
- `radio-service` — `ingress: internal`, invoked only by Cloud Tasks with OIDC. Owns
  the rotation clock, poll lifecycle, and Modal dispatch.

Write ownership is partitioned, with no document written by two components:

| Path | Writer |
|------|--------|
| `station/current` | `radio-service` only |
| `polls/{pollId}` (the poll document) | `radio-service` only |
| `polls/{pollId}/votes/{uid}` | `station-api` only |
| `songs/{songId}` — creation, `playCount`, `lastPlayedAt` | `radio-service` |
| `songs/{songId}` — `status: ready`, `objectPath`, `durationMs`, `title`, `artist` | the Modal worker (D5, D10) |

Rejected: splitting by domain (a poll service and a radio service, as originally
briefed). Poll opening is pinned to song start, so both services would write station
state and ownership of the rotation clock would be ambiguous; the radio service would
also absorb all listener read traffic.

Rejected: a single service. Listener reads and the GPU-spending control plane would
scale and fail together.

v1's `encoder` is deleted — the Modal container already has ffmpeg (D5).
`modal-dispatch-service` folds into `radio-service`; a `.spawn()` is a
sub-millisecond call and does not need its own deployment. `vote-api` and
`playback-stream` merge into `station-api`. Five services and three functions become
two services.

### D4 — Queue depth 1, plus an invisible fallback backlog

The poll winner becomes the literal next track. The visible queue is
`[current, next]`.

Separately, every song that ever reaches `status: ready` joins a fallback pool used
only when a generation misses its deadline or fails. The pool is a query, not a
collection: `songs where status == ready` ordered by `playCount asc, lastPlayedAt
asc`. A song that generates too late to play on its own poll still joins the pool, so
no successful generation is ever wasted.

Rejected: a pipelined depth-3 queue. Generation would get ~15 minutes of slack, but
the gap between voting and hearing the result would be ~10 minutes, destroying the
causal link that makes voting feel worthwhile.

### D5 — The Modal worker encodes and writes Firestore directly

The worker generates, transcodes to `.m4a` with ffmpeg in-container, uploads the
final object, then writes `songs/{songId}` with `status: ready` and `durationMs`.

This deletes v1's encoder service and its Eventarc trigger, and removes the
propagation delay between generation finishing and the song being usable.

Cost: Modal needs Firestore write permissions, and a container dying between upload
and write leaves an orphan object. `/tick` reconciles (F6).

### D6 — Tallies are hidden until the poll closes

The design handoff shows no percentages in either open state, and reveals them only
in the two closed states. Results are revealed at poll close (not at track end —
see D7).

Consequence: tallies are computed exactly once, at close, into an immutable
`tallySnapshot`. There is no live tally read path, no COUNT aggregation on the hot
path, and no tally cache. A closed poll's payload never changes, so it caches
indefinitely rather than expiring every second.

### D7 — Results reveal at poll close

Closed means revealed. The state machine is
`OPEN(unvoted) → OPEN(voted) → CLOSED(won|lost)` with no third timer.

This contradicts the handoff's `RESULTS AT TRACK END` copy, which must change. The
replacement is a live countdown, `RESULTS IN M:SS`, rendered in Doto — consistent
with the design's existing use of Doto for timecodes. A static
`RESULTS AT VOTE CLOSE` is the fallback if the countdown proves noisy.

Accepted tradeoff: the winning vibe is visible for roughly the generation window
(~2 minutes) before the track it produced starts playing.

### D8 — Cloud Tasks self-chaining drives the clock

Each rotation schedules the next `/tick` at `endAt` and a `/poll-close` at
`endAt - GENERATION_LEAD_MS`, using deterministic, versioned task IDs.

Rejected: Cloud Scheduler. Its one-minute floor cannot hit song boundaries.
Rejected: an in-process loop. It requires `min_instances: 1` and breaks with more
than one instance.

### D9 — Firebase Auth (Google), validated at the gateway

API Gateway validates Firebase ID tokens against issuer
`https://securetoken.google.com/{project}` and forwards verified claims, so
`station-api` reads a trusted `uid` from a header and never calls the Firebase Admin
SDK.

Anonymous auth is excluded. It would let one person mint unlimited identities, which
makes "authenticated" meaningless for the only reason voting is gated.

### D10 — Track titles and artist names are generated with the song

The design displays a track title (`Nightshift Drift`) and an artist line
(`SABLE UNIT`), and nothing in the brief says where they come from. They are produced
by the Modal worker alongside the audio and written into `songs/{songId}` in the same
`status: ready` write, so a song is never playable without a name.

Generation is deterministic from the winning descriptor plus the song id: a
two-word title drawn from curated word banks seeded by the song id, and an artist
name drawn the same way. No second model call, no external service, no failure mode
that can block a finished track from playing.

Rejected: an LLM call per track. It adds a dependency and a latency budget inside the
generation window to name something that is on screen for three minutes.

### D11 — Rate limiting is not the gateway's job

Google API Gateway enforces quota per API key or consumer project, not per end user.
It cannot express "N votes per user per minute".

This does not matter for `/v1/vote`: the create-only vote document caps a user at
exactly one vote per poll, which is a stronger guarantee than a rate limit. For read
floods on `/v1/state`, the control is `Cache-Control: public, max-age=1` at the CDN,
which collapses a listener stampede into one origin request per second.

This is recorded explicitly because the gateway was chosen partly for rate limiting,
and it does not deliver that in the form usually expected.

## Architecture

```
Browser · React SPA on Firebase Hosting
  │ Firebase Auth (Google) → ID token in Authorization: Bearer
  ▼
Google API Gateway
  ├─ GET  /v1/state           → station-api   (open)
  ├─ GET  /v1/queue           → station-api   (open)
  ├─ POST /v1/vote            → station-api   (JWT required)
  └─ GET  /v1/vote?pollId=    → station-api   (JWT required)

station-api · Cloud Run, public, callable only by the gateway service account
  reads   station/current, polls/{pollId}, songs/{id}
  writes  polls/{pollId}/votes/{uid}   ← create-only

radio-service · Cloud Run, ingress=internal, OIDC from Cloud Tasks only
  POST /tick         rotate, open poll, warm Modal, chain next tasks
  POST /poll-close   close poll, tally, pick winner, spawn generation
  POST /scaledown    min_containers=0, log generation outcome
  writes station/current, poll documents, song creation and play counters

Modal · ACE-Step on L4, GPU snapshot
  generate → ffmpeg → m4a → GCS upload → write songs/{id} status=ready

GCS bucket (public read, CORS enabled) + Cloud CDN → audio delivery
```

## Data model (Firestore)

```
station/current
  songId, startAt, endAt, durationMs
  nextSongId, nextStatus: generating | ready | fallback
  pollId, version                        ← monotonic; guards every rotation
  # title, artist, descriptor deliberately NOT stored here (diverges from an
  # earlier draft of this table): station-api reads them off songs/{songId}
  # instead, so there is one copy of song metadata, not a denormalised one
  # that could drift from it.

polls/{pollId}
  songId, opensAt, closesAt
  status: OPEN | CLOSED
  options: [{ key, descriptor, mood, genre, energy }] × 4
  winner: key | null
  tallySnapshot: { key: count } | null   ← written once at close, immutable

polls/{pollId}/votes/{uid}               ← create-only; existence is the dedupe
  option, createdAt

songs/{songId}
  status: generating | ready | failed
  descriptor, mood, genre, energy, title, artist
  objectPath, durationMs
  pollId, playCount, lastPlayedAt
  generation: { modalCallId, startedAt }
```

Vote options are sampled from v1's `pulsefm-descriptors` table, which maps ~100
single-word vibes to `(mood, genre, energy)` triples. Each poll samples 4 distinct
descriptors, excluding recently used ones and biasing toward spread across the mood
axis so the options read as real alternatives.

## API surface

`GET /v1/state` — anonymous, cacheable, identical for every listener.

```jsonc
{
  "serverTime": "2026-07-28T12:00:00.000Z",
  "current": { "songId", "title", "artist", "descriptor", "url", "startAt", "endAt", "durationMs" },
  "next":    { "songId", "status": "generating|ready|fallback" },
  "poll": {
    "pollId", "status": "OPEN|CLOSED", "opensAt", "closesAt",
    "options": [{ "key", "label" }],
    "winner": "key|null",
    "results": [{ "key", "percent" }] // present only when status == CLOSED
  }
}
```

`GET /v1/queue` — `[current, next]`, anonymous.

`POST /v1/vote` — authenticated. Body `{ pollId, option }`. Returns
`200 { option }` on success, `409` on duplicate or closed, `400` on unknown option or
stale poll. The response is authoritative: a 200 means the vote is recorded, never a
promise that it will be. This inherits v1 ADR 0003's central lesson.

`GET /v1/vote?pollId=` — authenticated. Returns `{ option }` or `404`. Exists so a
page reload can restore the caller's own selection without making `/v1/state`
per-user and uncacheable.

Percentages use largest-remainder rounding so they sum to exactly 100. Naive
per-option rounding produces 99 or 101 often enough to look broken.

## Timing

```
t = 0          /tick
                 promote next → current (or pull from fallback pool)
                 bump version, write station/current
                 open poll with 4 sampled descriptors
                 warm Modal (min_containers = 1)
                 chain /poll-close at endAt − LEAD, /tick at endAt

t = D − LEAD   /poll-close
                 transaction: OPEN → CLOSED, read tally, write winner + tallySnapshot
                 create songs/{new} status=generating
                 Modal .spawn() onto the already-warm container
                 set nextSongId, nextStatus=generating
                 chain /scaledown at + HORIZON

t ≈ D − LEAD   Modal: generate → ffmpeg → m4a → GCS → write status=ready
      + ~90s

t = D          /tick — nextStatus == ready ? promote : pull from fallback pool
```

Warming at poll *open* rather than poll *close* is what makes the deadline safe: the
GPU container is hot by the time the winner is known, so generation runs ~60–90s
instead of paying a cold start. With `GENERATION_LEAD_MS` at 120s on a ~3:30 track,
the poll is open ~90s and generation has ~120s of headroom.

All timing values are configuration. `closesAt` is derived as
`startAt + durationMs - GENERATION_LEAD_MS`, floored so that a short track still
leaves a minimum voting window (`MIN_POLL_WINDOW_MS`, default 45s).

Modal dispatch is fire-and-forget via `.spawn()`, with scale-down owned by a delayed,
idempotent, per-song Cloud Task rather than the tail of a long-lived request. This is
v1 ADR 0004 carried over unchanged: a handler that blocks on generation can be killed
mid-flight and strand `min_containers = 1`, paying for a warm GPU indefinitely.

## Failure modes

| ID | Condition | Behaviour |
|----|-----------|-----------|
| F1 | Generation overruns `LEAD` | `/tick` sees `nextStatus != ready` and pulls the least-recently-played song from the fallback pool. The late song still lands `ready` and joins the pool. |
| F2 | Generation fails | `/scaledown` polls the stored Modal call id, logs ERROR, marks `status: failed`. Same fallback. Nothing retries. |
| F3 | Cloud Tasks double-delivers `/tick` | Deterministic task IDs plus a `version` check inside the rotation transaction. A stale-version tick is a no-op. |
| F4 | Two instances race a rotation | Firestore transaction on `station/current` guarded by `version`. Exactly one wins. |
| F5 | Vote arrives after close | `station-api` rejects on `closesAt` wall clock with 409. A vote created after the tally read is orphaned; `tallySnapshot` is immutable. |
| F6 | Modal uploads but its Firestore write dies | Orphan object. `/tick` reconciles: when Firestore says `generating` past deadline, probe GCS for the object directly (strongly consistent for direct reads) and adopt it. |
| F7 | Empty fallback pool at launch | Seed the bucket with pre-generated tracks before first boot. An explicit slice-0 task, not an assumption — day one has no pool and the first generation is a cold start. |
| F8 | Client clock skew or background-tab throttling | `/v1/state` returns `serverTime`; the client computes an offset once per poll and does all countdown and seek maths against it. |
| F9 | Modal scale-down task lost | The next cycle's warmup/scaledown pair bounds how long `min_containers = 1` can persist. |

## Frontend

**Stack.** Vite + React 19 + TypeScript + Tailwind v4, static on Firebase Hosting
with an SPA rewrite. Not Next.js: Firebase Hosting only serves Next.js through Cloud
Functions or App Hosting, and nothing here wants SSR. The handoff ships v4 `@theme`
tokens that paste in directly.

**Station state.** One `useStation()` hook polls `/v1/state` every 2s plus 0–500ms
jitter, wakes ~300ms after the known `endAt` boundary so changeovers feel instant,
and refetches immediately after a vote. UI transitions are derived by diffing
consecutive snapshots. This is v1's `pollDiff.ts` pattern and is worth porting
closely.

**Audio.** Dual `<audio>` slots, preloading the next track for gapless changeover
(v1's `useAudioSlots.ts`). Position comes from `audio.currentTime`, so the progress
rail and timecodes describe what the listener is actually hearing.

**Waveform.** Driven by a WebAudio `AnalyserNode` rather than the handoff's `amp()`
sine, which the handoff itself labels a placeholder for real analysis data.
**This has an infrastructure dependency:** analysing cross-origin audio requires
`crossOrigin="anonymous"` on the element and a CORS configuration on the bucket. Get
it wrong and the analyser silently returns zeros. Rendered to a single `<canvas>`
rather than 60 animated DOM nodes, and gated behind
`@media (prefers-reduced-motion: reduce)` → static paused state.

### Vote panel

Specified by the prototype markup in `Music Player Final.dc.html`, not by the
handoff README — the README was regenerated only for the nav change and still
describes the interactive core as "one play/pause toggle".

**Placement.** Inside the transport sheet. Desktop: a fixed 430px column at the right
of the sheet, `border-left: 1px solid rgb(242 241 239 / .14)`, `padding-left: 36px`;
the sheet's gap tightens from 40px to 36px to make room. Mobile: below the progress
row, `margin-top: 22px; padding-top: 20px`, matching `border-top`.

**Grid.** 2×2. Desktop `gap: 6px`, padding `9px 11px`, Doto 11px / `0.14em`. Mobile
`gap: 8px`, padding `14px 12px`, `0.12em` for a larger touch target. Above it, a Doto
10px / 600 / `0.2em` header row with a label at each end.

**States.**

| State | Header left / right | Options |
|-------|---------------------|---------|
| Poll active | `NEXT VIBE — PICK ONE` / `ONE VOTE ONLY` (mobile: `ONE VOTE`) | border `paper/26`, hover → accent border and accent text. No percentages. |
| Voted | `VOTE LOCKED` / `RESULTS IN M:SS` | yours: accent border, `bg-accent/24`, trailing `YOURS` in `#FF7A7E`. Others: `paper/12` border, `opacity: .32`. No percentages. |
| Closed, won | `VOTE CLOSED` / `YOUR PICK WON` in `#FF7A7E` | percentages and fill bars appear. Winner: accent border, `bg-accent/45`. Losers: `paper/16` border, `opacity: .55`, `bg-paper/12` fill. |
| Closed, lost | `VOTE CLOSED` / `{WINNER} WINS` at `opacity: .45` | your pick: accent border, `bg-accent/24`, `✓ NN%` in `#FF7A7E`. Winner: solid `paper` border, `bg-paper/22`. Others `opacity: .5`. |

**New token.** `#FF7A7E` appears in the markup as a lightened accent for use on ink
but is absent from the handoff's token table. It must be added as
`--color-accent-on-ink`.

### Authentication states

Nav renders `LOGOUT` when signed in and `LOGIN` when signed out — same anchor
treatment (`text-ink/45`, `tracking-[0.22em]`, hover to full opacity). Desktop keeps
`HOW IT WORKS` beside it; mobile shows the single item only, per the updated handoff.

Signed-out listeners still see the poll panel in its active state, with options
visible and hoverable. The header's right label reads `SIGN IN TO VOTE` instead of
`ONE VOTE ONLY`. Clicking an option opens the Google sign-in popup and submits the
held selection on success, so the click is never wasted.

Gating the view rather than the action would cost the main reason a listener would
want an account.

## Testing

Rotation planning, winner selection with tie-breaking, option sampling, stale-version
gating, and percentage rounding are **pure functions with no Firestore dependency**,
unit-tested directly. v1's `services/playback-service/pulsefm_playback_service/
logic.py` exists precisely because this logic was untestable while inline in a
transaction; that is the most valuable structural lesson to carry over.

The Firestore emulator covers transactional paths: rotation under concurrent ticks,
vote dedupe under concurrent submissions, and poll close.

The OpenAPI specification gets contract tests so the gateway and `station-api` cannot
drift.

Frontend: unit tests on the snapshot-diffing logic and the clock-offset maths;
component tests over the four vote states plus both auth states.

## Delivery slices

Each slice is independently shippable and ends with a portfolio editorial post.

| Slice | Scope | Proves |
|-------|-------|--------|
| **0 — Foundations** | Repo scaffold, Terraform (bucket + CDN + CORS, Firestore, Artifact Registry, service accounts), CI, seeded fallback tracks | The project deploys |
| **1 — Thin vertical loop** | `/tick` rotating a fixed seeded playlist, `GET /v1/state`, React player in sync. No polls, no Modal, no auth | Clock sync, seek, and gapless audio in a real browser — the riskiest unknown, isolated and cheap to test |
| **2 — Generation** | Modal worker: descriptor → ACE-Step → ffmpeg → GCS → Firestore, dispatched on a timer | The GPU path and generation latency, before product logic depends on it |
| **3 — Polls and voting** | Poll lifecycle, option sampling, tally, winner → generation. API Gateway + Firebase Auth. The vote panel | The product |
| **4 — Hardening** | Reconciliation sweep, observability, analyser waveform, reduced-motion, error and offline states | It survives contact |

The ordering is deliberate: the two things most likely to fail embarrassingly —
browser audio sync and GPU generation latency — are proven in slices 1 and 2, before
auth and gateway complexity land on top of them.

**Each slice gets its own implementation plan.** This document is the design for the
whole system; it is deliberately larger than one plan's worth of work. Slices 0 and 1
are planned together (foundations are meaningless without something running on them);
slices 2, 3, and 4 each get a plan written when the preceding slice lands, so that
measured facts — real generation latency, real audio sync behaviour — inform the plan
rather than being guessed at up front.

## Portfolio

The portfolio at `~/Documents/repos/portfolio` already has a PulseFM entry at
`content/projects/pulsefm/`, and it is stale: `index.md` advertises Server-Sent
Events, five Python services, four Cloud Functions, and Memorystore Redis. v1 itself
deleted SSE (ADR 0002) and the tally function (ADR 0003), so the page misdescribes
even the system that exists today.

Approach: one project entry, not two. Content is filesystem-walked, so adding docs or
posts needs no registry edit; only `lib/data.ts:94` holds the card and the repo URL.

- **Editorial posts** — one per delivery slice, written as that slice completes,
  derived from its ADR or spec while the reasoning is fresh. Posts live in
  `content/projects/pulsefm/posts/`.
- **Doc pages** — `index`, `problem`, `solution`, `architecture`, `challenges`,
  `results` rewritten once, after the architecture stops moving. Writing them earlier
  means rewriting them every slice.
- **`lib/data.ts:94`** — update the `repo` URL to the v2 repository.

These are plan tasks, not intentions. A portfolio step that is not in the checklist
does not happen — which is how the current `index.md` came to describe SSE.

  brief specifies ACE-Step 1.5. The exact model identifier and its generation API
  must be confirmed at the top of slice 2 rather than assumed; if 1.5 changes the
  interface, the change is contained to the worker.
